# Company-scoped customer filtering with loading coordination

The change adds company buttons that synchronously filter customer rows, keeps the page-level loading overlay visible while the first newly visible customer is selected, and reuses the global fetch loading counter for nested requests. Rendering the buttons reapplies the current filter without changing selection, while `ALL` restores all rows. The loading sequence paints before filtering and waits through selection rendering, but empty filters retain stale selection state and overlapping clicks can let an older operation overwrite the latest company pane. **Watch for:** **[Medium, confirmed]** zero-result company filters leave hidden customer data selected; **[Medium, confirmed]** overlapping company clicks can finish out of order and restore the wrong contract pane.

**Verdict**: NEEDS_CHANGES

## High-level view

The click path holds an explicit loading reference across the pre-filter paint, synchronous filtering, first-visible selection, and final paint. Nested fetches use separate references, so they cannot close the overlay while the filter operation is still active.

`renderCompanyTabs` reapplies the filter with selection disabled, making its `applyCustomerCompanyFilter(..., false)` call synchronous despite the async declaration. `ALL` retains the current customer when it remains visible. The previous expanded-card, async expansion reversal, and inactive-selected background findings are resolved by collapsing non-selected cards, preserving expansion during card replacement, and targeting inactive selected cells respectively.

Companies from master data remain clickable at zero count, leaving the hidden previous customer selected when no rows match. Concurrent handlers also lack a latest-filter guard, allowing stale post-selection pane updates to win.

## Zero-result companies retain a hidden active customer

**[Medium, confirmed]** `renderCompanyTabs` creates a button for every master company, including companies whose count is zero (`webCRM/wwwroot/js/customerDetail.js:211-229`). When that filter is selected, `applyCustomerCompanyFilter` hides the active row, finds no first visible row, and exits without clearing `active-row`, `selected-contract-row`, expansion, or the customer and contract details (`webCRM/wwwroot/js/customerDetail.js:151-189`). The table reports zero visible customers while the detail panels still represent the hidden previous selection.

Disable or omit zero-count company buttons, or explicitly clear selection, expansion, and detail panels when `visibleCount` is zero.

## Overlapping filter clicks allow stale completion to win

**[Medium, confirmed]** Every company click starts an independent async handler with no request ID or active-company check around completion (`webCRM/wwwroot/js/customerDetail.js:991-1022`). `applyCustomerCompanyFilter` can await PDPA and contact work for the first visible customer; afterward, the handler unconditionally calls `showContractCompanyPane(company)` and updates the global loading message. A later click can finish first, then an older click can switch the contract pane back even though the newer filter button and row visibility remain active.

Give filter operations a monotonically increasing request ID and skip post-await UI work for stale IDs, or serialize/cancel company transitions. Keep each operation's loading-counter decrement in `finally` so overlap cannot hide the overlay early.
