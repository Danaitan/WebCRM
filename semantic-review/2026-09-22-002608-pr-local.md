# Filter-wide select-all for the Prospect Phase 3 table

The header checkbox now selects and deselects every row that matches the current DataTables filter across all pages, not just the rendered page. A shared `getProspectRowState` derives each row's selection and disabled flags from the persistent state maps, `applyProspectRowSelection` mutates `manuallySelectedCustomers`/`removedBatchCustomerIds` the same way for both the header and per-row paths, and `getFilteredProspectItems` feeds both the bulk toggle and the header's all/indeterminate computation from the full filtered set. After a bulk toggle the table is redrawn so checkboxes on other pages regenerate from state. This directly addresses the prior review's note that select-all only touched the rendered page. **Watch for:** **[Medium, confirmed]** every single-row toggle and every page turn recomputes `getProspectRowState` over the entire filtered set (up to ~63k rows × batch/customer scans), so large campaigns will feel the cost; **[Low, confirmed]** the header handler relies on the redraw's `drawCallback` to refresh the header all/indeterminate state rather than calling `updateCheckAllStatus` itself.

**Verdict**: APPROVED

## High-level view

The bulk toggle reads all filtered rows from DataTables (`rows({ search: 'applied' })`), skips rows whose `getProspectRowState` reports `isDisabled`, and routes each selectable row through the same `applyProspectRowSelection` used by per-row clicks. Because selection lives in `manuallySelectedCustomers` and `removedBatchCustomerIds` and the checkbox column renders from `getProspectRowState`, an `invalidate('data').draw('page')` after the toggle is what makes off-page checkboxes reflect the new state; there is no attempt to reach unrendered DOM directly.

The all-vs-indeterminate decision is computed over the same full filtered set, filtering out disabled rows, so the header reflects filter-wide truth rather than the current page. It is unchecked when nothing selectable is checked, fully checked only when every selectable row is checked, and indeterminate in between.

There is no infinite draw loop. `drawCallback` calls `bindTableCheckboxEvents`, but that function only attaches listeners and reads state — it never calls `draw`. The single `draw('page')` lives inside the header change handler and fires only on a user toggle, so a draw triggers one re-bind, not another draw.

The remaining concern is cost, not correctness: the header status recompute and the bulk loop both walk the entire filtered dataset, and `getProspectRowState` does linear scans of `currentProductBatches` and `currentBatchCustomers` per row, on every per-row toggle and every page navigation.

## Bulk toggle spans all pages through DataTables, not the DOM

`getFilteredProspectItems` returns `prospectTable.rows({ search: 'applied' }).data().toArray()`, i.e. every row matching the active search across all pages, independent of what `deferRender` has materialized. The header change handler iterates that array, and for each row calls `getProspectRowState`; only rows with a non-empty `idStr` and `!isDisabled` are passed to `applyProspectRowSelection`. This satisfies the "all rows matching the current filter across all pages" and "skip disabled rows" requirements without touching unrendered DOM.

The subsequent `rowCheckboxes.forEach(... checkbox.checked = isChecked)` over the captured NodeList is redundant with the redraw that follows — the `invalidate('data').draw('page')` re-renders the current page from state anyway — but it is harmless.

## State stays consistent because both paths share one mutator

`applyProspectRowSelection` is the single writer for selection state. On check it clears the id from `removedBatchCustomerIds` and, unless the row is already a saved batch customer, adds it to `manuallySelectedCustomers`. On uncheck it deletes from `manuallySelectedCustomers`, adds to `removedBatchCustomerIds`, and splices any matching entry out of `currentBatchCustomers`. Both the header bulk loop and the per-row handler call it with the same `state` shape, so a batch customer removed via select-all is recorded identically to one removed by an individual click. `getSelectedList`/`updateSelectedList` read from these same maps, so the sidebar reflects the bulk change after the single `updateSelectedList()` call at the end of the handler.

## Off-page checkboxes refresh via re-render, not direct mutation

The checkbox column is `data: null` with a `display` renderer that calls `renderProspectCheckbox` → `getProspectRowState`, so a checkbox's rendered `checked`/`disabled` is a pure function of the persistent state. That is why `prospectTable.rows().invalidate('data').draw('page')` is sufficient to bring every page into line: invalidating the cached row data forces the renderer to re-run against the freshly mutated maps the next time each page is drawn. This is the correct mechanism for "refresh checkboxes on other pages via redraw."

## All / indeterminate reflects the filter-wide set

`updateCheckAllStatus` builds `selectableStates` from `getFilteredProspectItems().map(getProspectRowState).filter(s => s.idStr && !s.isDisabled)`, then sets `checked` only when `checkedCount === selectableStates.length` (with a non-empty guard) and `indeterminate` when some but not all are checked. Because the source is the full filtered set with disabled rows excluded, the header reflects selection across all pages rather than the visible page. The `cloneNode(true)` in `bindTableCheckboxEvents` does not carry over the live `indeterminate`/`checked` properties, but `updateCheckAllStatus` runs at the end of `bindTableCheckboxEvents` and re-applies both on the new element, so the cloned header is corrected on every bind.

## No infinite draw recursion

The concern is that `drawCallback` calls `bindTableCheckboxEvents`, which could in turn cause another draw. It does not: `bindTableCheckboxEvents` only clones/re-binds the header checkbox, attaches per-row `change` listeners, and calls `updateCheckAllStatus` and `updateSelectedList`, none of which call `draw`. The only `draw('page')` in this cluster is inside the header `change` handler and executes solely on a user toggle. So the chain is user toggle → one `draw('page')` → one `drawCallback` → one `bindTableCheckboxEvents`, with no self-sustaining loop. Per-row toggles call `updateCheckAllStatus`/`updateSelectedList` and never draw. Confirmed safe.

## Cost of the full-set recompute

`getProspectRowState` is not cheap per row: it runs `currentProductBatches.find(...)` and `currentBatchCustomers.some(...)`, each a linear scan. `updateCheckAllStatus` applies it to every filtered row and runs on every per-row `change` event and every `drawCallback`. On the ~63k-row full-fetch table described in the prior review, toggling a single row triggers a full-dataset pass with nested batch scans, and each page navigation does the same. This is a behavioral cost regression worth addressing — for example by tracking selectable/selected counts incrementally in the selection maps, or memoizing row state keyed by id — before shipping on the large campaigns this feature targets.
