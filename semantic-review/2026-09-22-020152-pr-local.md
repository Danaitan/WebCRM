# Hide already-selected customers from the prospect list

Prospect rows that are already selected (persisted batch customers plus manually-ticked ones) are now filtered out of the "customer list" DataTable so they can't be picked twice. `getAllSelectedIdnos` unions `getPersistedSelectedIdnos()` (batch, minus removed) with the idno of every entry in `manuallySelectedCustomers`, and `loadProspectList` drops any fetched row whose idno is in that set. Interactive removal is layered on top: ticking a row deletes it from the table via `row(tr).remove().draw(false)`, select-all deletes every matching row through `removeSelectedRowsFromProspectTable(idnoSet)`, and the × button in the selected list re-runs `loadProspectList` to bring rows back. All table mutations are client-side over data re-fetched from the server, so nothing is permanently destroyed.

Watch for: a stale-cache correctness bug in `updateCheckAllStatus` — after per-row `row.remove()` the search key is unchanged, so `refreshSelectableRowIdStrs` skips recompute and the select-all header can misreport its state (confirmed). Secondary: the removal identifier used by `removeSelectedRowsFromProspectTable` (idno) differs from the identifier used everywhere else in selection state (id/idStr), an asymmetry that can leave rows un-removed when id and idno diverge (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The dedup-and-filter core in `loadProspectList` is sound: it re-fetches from the server each time, dedups by normalized idno, then subtracts `getAllSelectedIdnos()`. Because every table mutation operates on this freshly-fetched client copy, there is no permanent data-loss path and the × button reliably restores rows. The abort/requestId guarding around the fetch is correct and prevents stale responses from overwriting a newer load.

The DataTables API calls are used correctly for 1.13.6: `row(tr).any()` guards a removal, `rows((idx,data)=>...)` uses the supported function-selector signature, and `rows({page:'current'}).invalidate('data').draw(false)` is the right way to re-sync visible checkboxes on deselect.

The real defect is in the check-all bookkeeping. `refreshSelectableRowIdStrs` only recomputes when the search term changes, but per-row `row.remove()` shrinks the table without touching the search term, leaving `selectableRowIdStrs` holding idStrs of rows that are no longer in the table. `updateCheckAllStatus` then compares selection maps against a stale, oversized list, which can drive the header checkbox to the wrong checked/indeterminate value until the next full render resets the cache key.

A second, quieter inconsistency: selection state is keyed on `idStr` (prefers `id`, falls back to idno), but `removeSelectedRowsFromProspectTable` and the fetch-time filter match on `idno`. When a row has both an `id` and a different `idno`, the two identifier spaces don't line up, so select-all can fail to remove a row it just marked selected.

<summary>Issues (3)</summary>

1. **Stale selectableRowIdStrs after row.remove()** — per-row tick removes a row from DataTables but leaves the search key unchanged, so `refreshSelectableRowIdStrs` skips recompute and `updateCheckAllStatus` counts against rows that no longer exist. Force a recompute after a structural change: call `refreshSelectableRowIdStrs(true)` (or reset `selectableRowIdStrsKey = null`) right after `row.remove()`/`removeSelectedRowsFromProspectTable`, before `updateCheckAllStatus`.
2. **id vs idno mismatch in row removal** — selection state keys on `idStr` (id first) while `removeSelectedRowsFromProspectTable` and the load-time filter key on `idno`; rows whose id ≠ idno can be marked selected but not removed. Make removal match on the same identifier resolution used by `getProspectRowState` (compare both id and idno), or key the whole pipeline consistently on idno.
3. **select-all does not refresh header state** — the select-all handler calls `updateSelectedList()` but not `updateCheckAllStatus()`, and it reads live table data while the header logic reads the cached list; after issue 1 is fixed, add an `updateCheckAllStatus()` call at the end of the select-all branch so the header reflects the post-removal set.

<summary>Details</summary>

### DataTables API usage (verification requested)

The three flagged calls are valid for 1.13.6. `row(tr).any()` returns false when the checkbox's `<tr>` is detached, so the `row.remove()` guard skips gracefully. `rows((idx, data) => ...)` uses the function-selector form whose `data` argument is the row data object, matching how the predicate reads `data.idno`. `rows({ page: 'current' }).invalidate('data').draw(false)` correctly re-runs the checkbox column `render` against the mutated selection maps without a full reload.

### Stale selectable cache breaks check-all after per-row removal

`refreshSelectableRowIdStrs` short-circuits unless `force` is set or the search term changed:

```js
const searchKey = ($prospectSearchInput.val() || '').trim().toLowerCase();
if (!force && searchKey === selectableRowIdStrsKey) return;
```

The per-row `change` handler removes the row from the table and then calls `updateCheckAllStatus()`, which calls `refreshSelectableRowIdStrs()` with no force flag. The search term hasn't changed, so the cache is not rebuilt and `selectableRowIdStrs` still contains the idStr of the row that was just deleted from the table. `updateCheckAllStatus` then iterates that stale list:

```js
const selectable = selectableRowIdStrs;      // still includes removed rows
let checkedCount = 0;
for (const idStr of selectable) { ... }
const allChecked = selectable.length > 0 && checkedCount === selectable.length;
```

A just-ticked-and-removed row is still counted in both `checkedCount` and `selectable.length`, so the "all checked" arithmetic stays consistent only when the stale list and the live table happen to agree. Any check-all evaluation between a per-row `remove()` and the next full render reads counts for rows that are gone, so the header checkbox can show checked/indeterminate states that don't match what's selectable on screen. `renderProspectDataTable` resets the cache key (`selectableRowIdStrsKey = null`) only on a full render, not after an in-place `row.remove()`, so the divergence window is real.

Fix: after any structural mutation that isn't a full re-render (`row.remove()` in the per-row handler, and `removeSelectedRowsFromProspectTable` in select-all), invalidate the cache before recomputing — either `selectableRowIdStrsKey = null` or `refreshSelectableRowIdStrs(true)` immediately before `updateCheckAllStatus()`.

### Removal keys on idno while selection keys on idStr

`getProspectRowState` computes `idStr` as `id` when present, otherwise idno:

```js
const idStr = id && id !== '-' ? String(id).trim()
            : (idno && idno !== '-' ? String(idno).trim() : '');
```

Selection state (`manuallySelectedCustomers`, `removedBatchCustomerIds`, `applyProspectRowSelection`) is keyed on `idStr`. But the table-removal helper and the load-time filter both key on idno:

```js
// removeSelectedRowsFromProspectTable
const idno = normalizeIdno(data && data.idno);
return idno && idnoSet.has(idno);

// loadProspectList filter
const selectedIdnos = getAllSelectedIdnos();
return isRowInCampaignBranch(...) && (!idno || !selectedIdnos.has(idno));
```

`getAllSelectedIdnos` bridges the two identifier spaces for manual entries because it stores `idno` on the map value and reads `item?.idno`, so the fetch-time filter is correct. The gap: select-all builds `selectedIdnos` from `item.idno`, so a row with a usable `id` but blank or `'-'` idno gets marked selected (idStr derived from id) yet contributes nothing to `selectedIdnos` — it is not removed from the table even though it was just selected, leaving a selected row visible in the customer list. Whether this fires depends on the data; if idno is always populated it is latent, hence "likely" not "confirmed." Align the removal predicate with the same id-or-idno resolution `getProspectRowState` uses, or guarantee idno is present for every selectable row.

### Select-all header state is not refreshed and reads a different source

The select-all handler resolves rows via `getFilteredProspectItems()` (live `rows({search:'applied'}).data()`), applies selection, removes rows, then calls `updateSelectedList()` — but not `updateCheckAllStatus()`. The header checkbox reflects the user's own toggle so it looks right immediately, but its cached `selectableRowIdStrs` is now stale for the same reason as the per-row path. The next `updateCheckAllStatus()` (triggered by a later per-row change) will evaluate against a list that still names the removed rows. This is the same root cause as the first issue and should be fixed together: after `removeSelectedRowsFromProspectTable`, invalidate the cache and call `updateCheckAllStatus()` at the end of the select-all branch.

### No permanent data loss and no reload thrash

Every table mutation (`row.remove`, `removeSelectedRowsFromProspectTable`) operates on the client-side DataTables copy, which `loadProspectList` re-fetches from `GetProspect` on each load. The × button's `loadProspectList(currentProspectPage, currentProspectPageSize)` re-fetches and re-filters, so a de-selected customer reappears in the list — removal is presentation-only. The single `loadProspectList` call per × click, combined with `prospectAbortController.abort()` plus the `currentProspectRequestId` guard after the await, means rapid interactions cancel stale fetches rather than stacking renders. No double-reload or abort race is present in this path.
