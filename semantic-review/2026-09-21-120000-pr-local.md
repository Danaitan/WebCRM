# Full-fetch Prospect Phase 3 table with client-side paging and search

The change removes route-level pagination from the Prospect Phase 3 request and gives the full filtered result set to DataTables for client-side name search and pagination. DataTables keeps the records in memory while `deferRender` limits the table body to the current page, and checkbox state is reconstructed from persistent selection maps on every draw. Server-side campaign filters still trigger a fresh full fetch, while import campaigns continue to source their rows from the ETL response. **Watch for:** **[High, confirmed]** campaign clicks can complete out of order before the freshness guard is created and can mix one campaign's filters/file with another campaign's selected rows; **[High, confirmed]** stale or aborted prospect/campaign requests leak the shared loading counter and can leave the global overlay permanently visible.

**Verdict**: NEEDS_CHANGES

## High-level view

`CRMService.GetProspectPhase3` now calls `p2/getProspect_phase3` with filter query parameters rather than appending `{page}/{pageSize}`. The frontend passes the complete response into a client-side DataTable, searches only the name column, and uses DataTables paging; `deferRender` prevents all 63k rows from being eagerly materialized as DOM nodes.

Manual checkbox choices live in `manuallySelectedCustomers` and removals in `removedBatchCustomerIds`, so page and search redraws regenerate checkboxes from stable state rather than from the current DOM. The select-all operation applies to the currently rendered DataTables page, not all 63k records.

The request-ID checks around prospect refreshes prevent an old full-fetch response from replacing newer table data. Campaign switching is not fully protected because the campaign request ID is allocated only after awaiting file metadata, and selected-customer refreshes mutate shared state before their caller checks freshness.

The shared loading API is reference-counted. Both campaign and prospect refreshes skip `stopLoading()` for stale requests, so cancellation leaves unmatched loading references even though stale responses are correctly prevented from drawing.

<summary>Issues (2)</summary>

1. **[High, confirmed] Campaign switch can commit mixed state** — The freshness epoch is created after an unguarded file request, and selected-customer loaders mutate global state before freshness is rechecked. Create the epoch before any await, pass the captured campaign and cancellation/freshness token through every loader, and commit each result only while current.
2. **[High, confirmed] Stale requests leak the loading counter** — Prospect and campaign operations skip `stopLoading()` when superseded, leaving a reference-counted overlay stuck after ordinary rapid interactions. Balance every `startLoading()` with an unconditional `stopLoading()` in that operation's `finally` and use request IDs only to gate UI writes.

## Campaign freshness starts after an unguarded file request

**[High, confirmed]** A campaign click assigns `selectedCampaign`, clears selection state, and then awaits `displayCampaignFile(item.file_id)` before aborting the previous filter request or incrementing `currentFilterRequestId` (`webCRM/wwwroot/js/prospectSetup.js:624-668`). If campaign A's file request is slow and campaign B is clicked, B can progress first; when A's file request eventually completes, A creates the newest request ID and renders A's filter definition even though the global `selectedCampaign` still points to B. The file display itself is also unguarded, so A's filename can overwrite B's.

A second stale write exists after the guarded filter work. `refreshSelectedCampaignCustomers()` reads the global campaign, awaits a batch or ETL request, and then writes `currentBatchCustomers` and `currentProductBatches` with no request ID (`webCRM/wwwroot/js/prospectSetup.js:2140-2196`). The caller checks `currentFilterRequestId` only after those writes (`webCRM/wwwroot/js/prospectSetup.js:965-969`), allowing an older refresh to overwrite the newest campaign's selection sidebar even when it is prevented from rendering the prospect table.

Allocate the campaign epoch and abort prior work immediately after the click begins, before the first await. Pass a captured campaign code and the epoch/signal into file, batch, and ETL loaders; commit filename, filter markup, import mode, selected customers, and product batches only when that epoch is still current. The campaign-specific functions should not re-read `selectedCampaign` after awaiting network work.

## Stale requests leave unmatched loading references

**[High, confirmed]** `startLoading()` increments the shared `loadingCount`, while `stopLoading()` decrements it (`webCRM/wwwroot/js/site.js:6-25`). `loadProspectList()` starts a loading reference for every refresh but only stops it when its request ID is still current (`webCRM/wwwroot/js/prospectSetup.js:1391-1417`). Applying filters twice, changing campaigns during a full fetch, or superseding a non-abortable import ETL fetch leaves the older request's reference in the counter; the latest request removes only its own reference, leaving the global overlay visible.

The campaign click handler has the same imbalance: it calls `startLoading()` for each campaign operation but its `finally` calls `stopLoading()` only for the latest request (`webCRM/wwwroot/js/prospectSetup.js:674-676,1013-1017`). Request IDs should gate UI commits, not cleanup. Every operation that increments the loading counter must call `stopLoading()` unconditionally in its own `finally`; keep the freshness check around rendered state only.
