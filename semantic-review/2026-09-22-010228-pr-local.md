# Select-all fix for the prospect DataTable

The prospect table (up to ~63k rows, client-side, `deferRender: true`) got a rework of its select-all path. Row state now comes from a prebuilt `batchMatchIndex` (O(1) Set lookups instead of scanning batch arrays per row), the header check-all iterates every filtered row across all pages via `getFilteredProspectItems()` then forces the visible page to re-render with `rows({page:'current'}).invalidate('data').draw(false)`, and `updateCheckAllStatus()` evaluates a cached `selectableRowIdStrs` list instead of re-scanning the dataset on each draw. The core mechanics work: `invalidate('data')` does defeat the deferRender HTML cache so checkboxes repaint, and there is no draw recursion.

Watch for: `selectableRowIdStrs` is only rebuilt inside `renderProspectDataTable`, but the search box filters via `column(1).search().draw()` without re-rendering — so after any search, the check-all header status is computed against the pre-search row set, not the visible filtered set (**confirmed**). This is a correctness bug in the header state, not in the selection itself.

**Verdict**: NEEDS_CHANGES

## High-level view

The select-all correctness path is sound. Clicking the header applies selection to the full filtered set (`rows({search:'applied'})`), and the forced `invalidate('data').draw(false)` on the current page makes `renderProspectCheckbox` re-run against the freshly mutated `manuallySelectedCustomers` / `batchMatchIndex`, so visible checkboxes reflect the new state despite deferRender caching.

The performance rework is real and correctly scoped: `batchMatchIndex` is rebuilt once at the top of `renderProspectDataTable` before any row state is computed, and `getProspectRowState` reads it with Set lookups. `selectableRowIdStrs` is built in the same pass. Both are consistent immediately after a data load.

The staleness gap is `selectableRowIdStrs` (and by extension the check-all header state) drifting when the table is filtered by the search box, because search goes through `column(1).search().draw()` and never re-enters `renderProspectDataTable`. Selection still applies correctly (select-all reads live filtered rows), but the header checked/indeterminate state reflects the wrong denominator.

No infinite draw recursion exists: the draw callback rebinds events and calls `updateCheckAllStatus`, neither of which issues a draw.

<summary>Details</summary>

### Header click repaints the visible page correctly

The one non-obvious ordering that makes deferRender repaint work:

```js
prospectTable
    .rows({ page: 'current' })
    .invalidate('data')
    .draw(false);
```

`invalidate('data')` discards the cached rendered cell for the current-page rows, so the next draw re-invokes the column `render` callback → `renderProspectCheckbox(row)` → `getProspectRowState(item)`. The handler mutates `manuallySelectedCustomers` / `removedBatchCustomerIds` *before* the invalidate, and `getProspectRowState` computes `isChecked` live from those maps plus `batchMatchIndex`, so the repainted checkbox reflects the new selection. Scoping the invalidate to `page:'current'` rather than all rows is the right call for a 63k-row set — off-page rows repaint on their own draw. Selection spans pages because the handler applies to `getFilteredProspectItems()` = `rows({search:'applied'})`, not the DOM rows.

### batchMatchIndex / selectableRowIdStrs rebuild timing

`rebuildBatchMatchIndex()` runs at the top of `renderProspectDataTable`, before `selectableRowIdStrs` is built and before the table renders, so both caches are consistent with `currentProductBatches` / `currentBatchCustomers` on every data load. Save and campaign-change paths both funnel through `loadProspectList` → `renderProspectDataTable` (save calls `loadProspectList` after clearing `manuallySelectedCustomers`), so the indexes are not stale after those events.

The gap is search-driven filtering (**confirmed**):

```js
function filterProspectRows(searchText) {
    if (!prospectTable) return;
    prospectTable.column(1).search((searchText || '').trim()).draw();
}
```

This `.draw()` fires `drawCallback` → `bindTableCheckboxEvents` → `updateCheckAllStatus`, but never re-enters `renderProspectDataTable`, so `selectableRowIdStrs` still holds the ids computed from the *unfiltered* `tableData` at last render. `updateCheckAllStatus` then does:

```js
const selectable = selectableRowIdStrs;          // full set, not filtered
let checkedCount = 0;
for (const idStr of selectable) { ... }
const allChecked = selectable.length > 0 && checkedCount === selectable.length;
```

After a user searches to a subset, `selectable.length` is still the full-set count, so the header can show unchecked/indeterminate even when every visible filtered row is selected (or vice versa). Selection is unaffected because the header click reads live `rows({search:'applied'})`; only the checked/indeterminate indicator is wrong. Fix: recompute `selectableRowIdStrs` from the applied-search rows at status time — rebuild it inside `updateCheckAllStatus` (or `drawCallback`) via `prospectTable.rows({search:'applied'}).data().toArray().map(getProspectRowState)...`, or add the recompute to `filterProspectRows`. Rebuilding on every draw for 63k rows is the cost the cache was meant to avoid, so rebuilding only when the search term changes keeps the performance win.

### No draw recursion

The draw → callback chain terminates: `drawCallback` calls `bindTableCheckboxEvents` → `updateCheckAllStatus` / `updateSelectedList`, none of which issue a `draw`. The only draw inside an event path is the select-all handler's `invalidate('data').draw(false)`, fired by a user `change` event, not by `drawCallback`. No loop.
