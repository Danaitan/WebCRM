# "พบ X รายการ" total-found count derived from API total minus selection-hidden rows

The prospect list shows a "พบ X รายการ" (found N items) counter that must reflect the true API total minus any customers hidden from the list because they are already in the selected set. The implementation keeps two module-level values — `prospectAuthoritativeTotal` (fixed per API load) and `prospectHiddenBySelectionCount` (accumulated as rows are hidden) — and `updateProspectTotalFound` computes `total - hidden` in no-search mode, or defers to DataTables' post-filter `recordsDisplay` in search mode. The hidden count is recomputed from scratch on every `loadProspectList` and incremented in place on per-row check and select-all. The design is sound: the no-search formula is idempotent, so repeated `drawCallback` invocations do not double count, and reload always resets the hidden count from a fresh filter pass consistent with the current selection set.

Watch for: nothing blocking. The four required paths (initial load, per-row check, select-all, remove-item ×) all keep the counter correct, and search mode correctly shows the filtered count. One minor robustness note below (search/recordsDisplay is `confirmed` self-correcting, not a bug).

**Verdict**: APPROVED

## High-level view

The counter is driven by a single idempotent formula in no-search mode: `Math.max(0, prospectAuthoritativeTotal - prospectHiddenBySelectionCount)`. Both operands are stable between mutations — `prospectAuthoritativeTotal` is set once per API response and never touched by the increment paths, and `prospectHiddenBySelectionCount` is the only thing the check/select-all paths mutate. Because the displayed value is a pure function of those two variables (not an accumulator on the DOM text), the extra `updateProspectTotalFound(info.recordsDisplay)` call that fires from `drawCallback` on every `draw()` cannot double count — it recomputes the same result.

Reset correctness holds because `loadProspectList` recomputes `hiddenBySelectionCount` from the filter pass (`selectedIdnos.has(idno)`) and hard-assigns it to `prospectHiddenBySelectionCount`, rather than adding to it. The selection set it filters against (`getAllSelectedIdnos`) is populated by `applyProspectRowSelection` *before* the in-place increments happen, so a check followed by a reload lands on the same number by two different routes without drift.

The `recordsDisplay` fallback (`prospectTable.page.info().recordsDisplay` when the argument is omitted) is only consulted in search mode or when `prospectAuthoritativeTotal` is null; in the no-search case the argument is ignored entirely, so the fallback cannot corrupt the authoritative subtraction. Search mode intentionally bypasses the subtraction and shows DataTables' filtered count — the hidden count keeps accumulating in the background but is not consulted until search is cleared.

### Idempotent no-search formula defeats double counting

The suspected double-count vector is the interaction between the explicit increment paths and `drawCallback`. Per-row check does `row.remove(); prospectTable.draw(false); prospectHiddenBySelectionCount += 1; updateProspectTotalFound();` and select-all does `prospectHiddenBySelectionCount += removed; updateProspectTotalFound();`. Meanwhile `drawCallback` fires on every `draw()` and independently calls `updateProspectTotalFound(info.recordsDisplay)`.

This is safe because the no-search branch never reads `recordsDisplay` and never accumulates onto the previous displayed value:

```js
} else if (Number.isFinite(prospectAuthoritativeTotal)) {
    value = Math.max(0, prospectAuthoritativeTotal - (prospectHiddenBySelectionCount || 0));
}
```

`prospectAuthoritativeTotal` is assigned once per API response (`loadProspectList`) and is not mutated by any check/select-all path. `prospectHiddenBySelectionCount` is the sole mutated operand. So calling `updateProspectTotalFound` any number of times between mutations yields the same value — the `draw()`-triggered callback and the explicit call cannot compound. `confirmed`.

Note the ordering in the per-row handler: `row.remove()` and `draw(false)` run *before* `prospectHiddenBySelectionCount += 1`. The intermediate `drawCallback` from that `draw` computes with the pre-increment hidden count, then the explicit `updateProspectTotalFound()` immediately after the increment produces the final correct value. The transient intermediate value is overwritten in the same synchronous tick, so it is never observable. `confirmed`.

### Reload recomputes hidden count from the selection set, no drift

`loadProspectList` does not trust the accumulated counter across reloads — it rebuilds it:

```js
const selectedIdnos = getAllSelectedIdnos();
let hiddenBySelectionCount = 0;
const rawData = uniqueData.filter(item => {
    ...
    if (idno && selectedIdnos.has(idno)) { hiddenBySelectionCount++; return false; }
    return true;
});
prospectHiddenBySelectionCount = hiddenBySelectionCount;   // hard assign, not +=
```

The hard assignment is the correct reset semantics: whatever the counter accumulated through per-row/select-all is discarded and replaced by a count derived purely from the current API payload intersected with `getAllSelectedIdnos()`. This is what keeps the remove-item × path correct — that handler calls `loadProspectList(currentProspectPage, currentProspectPageSize)` after removing the item from `manuallySelectedCustomers`/`removedBatchCustomerIds`, so the recomputed hidden count naturally drops by one and the removed customer reappears in the list. `confirmed`.

Consistency between the increment path and the recompute path holds because `applyProspectRowSelection` writes into `manuallySelectedCustomers` before the `+= 1` runs, and `getAllSelectedIdnos` reads from that same map. A check-then-reload therefore reaches the same number whether it was incremented in place or recomputed. `confirmed`.

One caveat worth stating precisely: the recompute only counts customers hidden **within the current API payload** (`uniqueData` for the loaded page/window). If the API total counts rows that are not present in the returned payload but are in the selected set, the subtraction is only as accurate as the overlap between the payload and the selection set. For the 62,991 − 2 = 62,989 case this is correct because the two selected customers are in the payload being filtered. This is a property of the SP payload shape, not a defect in the counter logic, and is out of scope for this diff. `possible` (depends on SP behavior, not verifiable from the JS).

### Select-all uses the actual removed count, not the requested set size

Select-all computes the decrement from what DataTables actually removed rather than from the size of the requested idno set:

```js
const removed = removeSelectedRowsFromProspectTable(selectedIdnos);
prospectHiddenBySelectionCount += removed;
```

`removeSelectedRowsFromProspectTable` returns `rows.count()` before removal, so idnos in the set that are not present as table rows (already hidden, on a filtered-out branch, deduped) do not inflate the decrement. This avoids over-subtracting and driving the counter below the true visible reduction. `confirmed`.

### Search mode shows the filtered count and leaves the hidden count untouched

When the search box is non-empty, `updateProspectTotalFound` returns `recordsDisplay` (DataTables' post-filter count) and ignores `prospectAuthoritativeTotal`/`prospectHiddenBySelectionCount`:

```js
if (searchText) { value = recordsDisplay; }
```

`drawCallback` passes `info.recordsDisplay` explicitly, so during search the counter tracks the filtered result set as required. Checks performed while a search is active still increment `prospectHiddenBySelectionCount` in the background; that value is simply not consulted until search is cleared, at which point the no-search formula picks it up. So clearing search after selecting rows shows the correct `total - hidden`. `confirmed`.

The one informational observation: when `updateProspectTotalFound()` is called with no argument in search mode (the per-row check path), it falls back to `prospectTable.page.info().recordsDisplay`. Because the per-row path runs `row.remove()` + `draw(false)` before that call, the fallback reflects the already-reduced filtered count, so it is correct. If a future change reordered the removal after the `updateProspectTotalFound()` call, the fallback would read a stale (one-too-high) filtered count for a single frame. Not a current bug — flagged only so the ordering is preserved. `confirmed` self-correcting under current ordering.
